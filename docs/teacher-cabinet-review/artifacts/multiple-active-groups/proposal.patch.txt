+# Multiple active groups: Student/Teacher compatibility proposal
+
+Owner decision supersedes one-active-group for this operation. Pinned source 3dbb714f2f758c7dbe03548a71c161718cf9cb53 and root's verified catalog metadata. Review artifact only: no DDL, data, fixtures or authority change. Prior single-affinity Teacher roster/read/write candidates are held; they must not silently activate.
+
+## Current concrete coupling
+
+- Current ua_private.memberships primary key is person_id. It carries affinity_group_id, active, revision and epoch; people_membership_required is a deferred reverse FK from people.id to this singleton row. Student profile mirrors only active_group_id. Do not change the existing PK in place or turn that scalar into an array.
+- Grants are keyed (person_id, assignment_id) and reference the old membership person_id; an assignment references its group as well as a demo/version. storage/student-http-rows.ts:40–41 loads rostered and membershipEpoch from the singleton membership, and the corresponding student-http.ts currentGrant compares to profile.active_group_id. Simply adding a second group row/array would either hide valid access or use the wrong epoch.
+- Exam series remains keyed (person_id,demo_id); attempt rows are keyed by ID and unique person+demo+generation with assignment/demo FK. Current/official pointers have deferred matching attempt constraints. None of those keys change. An original running attempt, answers, deadlines and history are never reassigned or recreated.
+- Old first-test, membership activity/protection and transfer/removal paths use a single affinity/epoch and may revoke grants, pending recovery/notifications/review state on a transfer. They cannot run unmodified after multi-group writes are enabled. Account-deletion barriers, storage inventory and RLS also need reviewed awareness of the additive table; adding membership must not act as deletion or change technical history.
+
+## Target additive model and staged cutover
+
+1. Keep memberships and people.profile.active_group_id unchanged for legacy consumers. Introduce a separate canonical pair-membership relation conceptually keyed (person_id,group_id), with FKs to the same people/groups, current active flag, and an independent monotone safe revision and epoch per pair. Do not pick a schema migration or grant until reviewed. Verify separately whether an additive person-scoped membership-set revision is needed or use canonical active-pair set checks under existing person lock; do not reuse any group epoch as a person-wide fence.
+2. Backfill only real old affinities with observed active flag and exact revision/epoch, not a row for ungrouped users; leave no guessed relationship or group name. Validate existing singleton membership/profile/grant/assignment agreement first. Invalid cross-group legacy grants, detached assignments, archived groups, missing names and unmatched history are reported as reconciliation cases; no inherited stale grant may become valid. Existing primary/legacy profile link is a compatibility projection, not authorization. Never overwrite it based on a new Teacher add.
+3. In staged shadow comparison while old writes stay authoritative, derive each current grant through assignment.group_id plus the current membership for that exact person/group and compare that pair's epoch to grant_epoch. A grant to another group is not equivalent; detached group/invalid mapping cannot admit a new start. Historical read/active attempts stay anchored to their stored original person+assignment+demo+generation. Compare scopes, start eligibility and existing read/history outcomes on real authorized pilot data only. No automatic activation and no unreviewed dual writers.
+4. Before activation move all supported authorization/read/write surfaces together: currentGrant, grant loader, assignment roster enumeration, domain/RLS constraints, Teacher own-group roster, notification/review writes, and account deletion/barriers. Existing live single-membership PUT/transfer/removal paths must be explicitly flagged or gated if not compatible; they must not change pair data from an incomplete projection. To retain history, the old membership row and its deferred/FK relationships are not removed in this phase. A new snapshot that has multiple groups may not be safely down-converted; rollback disables new write scope first and must retain all pair rows to avoid silently discarding access/history.
+5. Adding an already active same pair is a no-op. Re-adding an inactive pair, if agreed for this action, uses only that group's new revision/epoch and never re-enables existing revoked/old-epoch grants. Do not create exam grants in the membership confirmation unless the independently approved assignment provisioning says so; no other group membership/grant/expiry, history or notifications changes. Removal/Owner/Admin transfer remain separate, explicitly pair-scoped design; no automatic movement across groups.
+
+## Pilot preview and confirmation
+
+- Teacher first selects an explicit active own group; the server verifies current Clerk/Teacher authority and exact nonrevoked group scope before directory lookup. Match a single real existing Student by exact canonical public cabinet ID. Current storage uses unique people.qadam_id, never accept both speculative renamed fields; use the deployed alias only after the existing separately reviewed rename. No partial search, email/phone/name matching, broad enumeration or URL identifier. Rate-limit and give generic not-found for malformed/unavailable/nonpermitted subjects with no side channel.
+- Return only active group display names for that selected Student, as explicitly confirmed by Owner. Do not return student peers, grades, private data, other group IDs, test details or association details. Real labels only, no placeholder UUID-as-name. A missing true label/uncertain completeness stays unavailable, not a fabricated empty list. Owner-approved pilot still needs genuine group metadata. Never log the public ID or names in unsolicited audit records.
+- Require explicit confirmation bound to the independently verified Teacher, exact own target group, looked-up canonical Student and preview state, with a short-lived server-verified opaque confirmation context or existing approved equivalent. At commit recheck Teacher authority and scope, enabled Student, current group, and membership set under existing canonical person/group lock. Re-read preview if active memberships changed before write. Nothing about receipt/audit or privacy retention is implied by preview; use only separately reviewed canonical immutable operation handling without retaining unnecessary identities.
+- One normal attempt per stable demo stays global to the Student. If both groups assign the same stable demo, choose the authorized group assignment for a first start only; after start use existing own attempt/receipt/history policy, never create a second normal attempt or move the original to the newly added group. Time is unchanged, including after original group close. Detail/solutions remain subject to original stored assignment review gate; adding another group is not a way around it.
+
+## First necessary decision before changing old transfer/remove
+
+Which exact source group should an Owner/Admin choose for a future “transfer” when a Student has multiple active groups? Recommended: explicitly selected source and destination, alter only that pair and preserve all unrelated pairs. This decision does not block the initial independent add if old transfer/removal are gated where ambiguous. Legacy displayed primary remains unchanged/non-authoritative by default; no auto-promotion of a new group. A more involved Student group picker is not implied by safe backend linkage.
