Existing reusable implementation: staff-http.ts handles provisional PUT /api/v1/admin/versions/{version_id}/questions/{question_id} and separate publish POST. It derives the trusted staff/person and checks current subject approval before handling the write. staff-content.ts::writeDraftQuestion enforces revision/frozen guards, distinct option IDs/one correct, unique draft position, operation replay and audit. publishDraft freezes an existing nonempty draft and applies existing grading rules. Do not reimplement either operation or infer assignment authority. The existing HTTP module is not mounted/configured as live Teacher authoring; this extension is not a way around that.

Local adapter takes only the server's current verified Teacher record and canonical existing draft target, checks exact form fields, four distinct stable option IDs and one selected correct ID, pins the existing expected revision, copies text/formula/explanation and optional exact individual points into the generated QuestionWrite shape, and returns a serialized request description for the canonical provisional path. It makes no network call and stores nothing. Image input is unavailable until the actual approved media path exists. Avoid interpreting repeat of an already prepared command as a duplicate entry; reuse the exact same payload and idempotency key if a deliberate recovery needs retry, not a new command preparation after server state may have changed. The authoritative staff service must still independently check scope, current revision, receipt and position under its transaction. No cloning, publish, assignment, draft creation, file ingestion, or fabricated labels/test rows are inferred.
