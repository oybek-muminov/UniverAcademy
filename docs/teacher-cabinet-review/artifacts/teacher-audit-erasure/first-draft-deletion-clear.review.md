# First-draft actor deletion-clear gate (review only)

Scope: private, internal gate for new and replayed first Teacher draft creation. It is not an account-deletion permission, public HTTP endpoint, job lookup, retention change, or executable SQL. Source pin: 3dbb714f2f758c7dbe03548a71c161718cf9cb53.

## Minimal proposal

Reuse the existing canonical deletion predicate, preferably through **one private, purpose-bound security-definer wrapper** inside the dedicated first-draft writer transaction. The wrapper accepts only the canonical current actor of that authenticated operation; it takes no second/target person ID, receipt, job ID, operation/table names, or raw Clerk/Student credential. It returns only clear/blocked to that trusted composition, with unknown/unavailable treated as blocked. Existing `assert_deletion_writable` can implement the canonical actor check internally using its fixed people/id branch, or the predicate can be factored into a private one-person helper used by both existing barriers and the new wrapper. Never grant EXECUTE directly on generic `assert_deletion_writable`, `assert_deletion_staff_writable`, status/recovery functions, or installer-owned roles. Do not use a write or treat a successful no-op as proof.

Security boundary: the trusted Worker independently verifies Clerk issuer, subject, enabled existing actor, liveness and lease; it derives the actor and acquires the canonical identity/person locks. The helper must reject absent, mismatched, invisible, or ambiguous actors, and must never receive an ID taken from HTTP. A mutable GUC or an actor UUID alone is not authentication. Keep EXECUTE confined to the isolated dedicated writer behind this one fixed application dispatch; no public/general invocation or arbitrary query interface sharing that credential. This is not cryptographic DB attestation of end-user identity against a holder of the dedicated writer credential. If that threat model must also be addressed, do not deploy a general actor-argument wrapper; require an independently verified DB-bound actor proof or a separately reviewed single purpose-bound command surface, not credential reuse or claimed GUC trust.

Canonical existing storage already keeps the privileged deletion blocker private under FORCE RLS. Do not give the Teacher writer SELECT on `account_deletion_jobs` or job/proof/receipt tables. Review whether existing deletion executor-owned private helper can stay the internal no-login owner; no membership, assume-role, connection, or extra public grants are given to the new writer. If refactoring to a different owner, require a separate no-login, non-owner-table, NOBYPASSRLS principal, complete proven policy visibility for only the deletion predicate, and no access to receipts/job payload or provider workflows.

## Lock and negative proof

- Use advisory lock on canonical Clerk identity → locked mapping row → same locked person, as in prepare/finalize. Run the gate on that same connection and transaction, after successful verified-auth/liveness and current role/scope checks, before receipt lookup or any draft write; recheck lease/abort through commit. Existing definer re-locking the same person in the same transaction is not a second connection. Do not change the ordering or take locks in a separate reader.
- Absence of a matching job must be authoritative and must include all states, even completed. The receipt-based status function's visibility window is not absence. Prove the statement reads a fresh, complete snapshot **after** acquiring the protecting lock; review transaction isolation/current snapshot semantics and that every future job creation/transition or alternate privileged path honors the same person lock. Under the intended normal isolation, earlier statements cannot supply a cached negative. If job policy suppresses rows, a helper result is missing or the transaction/actor cannot be established, fail closed. Do not rely on `people.enabled` as sole absence proof; atomic disabling in the current prepare is corroborating behavior, not a durable proof covering all deployed and future paths.
- Write triggers continue to provide existing race protection for new inserts, and this gate separately covers replay, which otherwise may perform no mutation. Reject on missing approval/configuration, unusual DB failure, result other than clear, or uncertain commit. No outward distinction that could leak another account's deletion state.

## Release and approvals

1. Re-read deployed function ownership, ACL, policies and lock contract with metadata only before proposing activation. Review the wrapper's exact argument/output and credential threat model; independently approve SQL, private EXECUTE/owner/config changes and rollout. No deletion role or credential reuse by the new Worker.
2. Install and verify the restricted wrapper/binding only under explicit approval; keep writer unmounted. With approved real pilot and rollback plan, demonstrate known-authorized clear, blocked, missing helper, expired actor, concurrency with prepare, and completed-job rejection without looking up another person's account; never present fixture-free static reasoning as runtime verification.
3. Only then wire new/replay gate; keep old write barrier, provider recovery and deletion locks as before. This gate only answers whether the actor is clear to begin/replay this operation. It does **not** clear the separate legacy audit/receipt erasure blocker or authorize enabling Teacher writes while that lifecycle still lacks approval.

## Decision addendum: pinned basis and smallest non-oracle pilot surface

The pinned database layer **cannot independently establish the authenticated request actor** under these constraints. Clerk verification/liveness happen in the Worker. The stored enabled issuer/subject mapping establishes who an identity belongs to, not that a SQL caller proved that identity. The pinned `trusted-server-context.ts` explicitly uses role-settable `set_config` values and calls them assertions, not authentication against a holder of the database credential. Its WeakMap is a Worker-adapter lifetime check. The identity/person locks serialize operations, not certify authentication. The existing generic deletion helpers accept caller-selected row/actor data; the status function requires its own receipt and returns job data. None is a scoped, independently authenticated actor primitive. Do not grant those helpers or treat stored hashes or supplied Clerk claims as proofs.

**Recommendation for a single approved actor, if exact isolation is feasible:** do not expose a standalone deletion-clear SQL call. Approve one private, purpose-bound first-draft command instead; its *internal* deletion predicate reuses the canonical fixed people/id helper under the existing lock. Give the dedicated Worker login EXECUTE on that one command only (no broad table/definer permissions, no other runtime/recovery/deletion credentials). As a distinct approval boundary, the database defines a private immutable-in-use mapping from that verified dedicated login principal to the **single owner-approved pilot Teacher and exact pilot scope**. The caller cannot change the mapping. The DB function accepts the bounded draft input and operation idempotency key, with **no caller-selected actor, issuer, subject, target-person parameter, or arbitrary action**. Resolve only that fixed identity and recheck its enabled canonical staff approval/scope under canonical locks, then before both lookup and write invoke the existing private assertion or its factored private predicate. Return only the normal acknowledged draft result or a generic unavailable response, never a deletion-status value, identifiers from a job, or replay receipts as a data interface. Compiler/type-only and no-worker fallback remains disabled until approved.

The fixed binding limits what the credential can do, but does **not** independently prove the human behind a request. The isolated Worker must still prove current Clerk identity/session/liveness, check exact match to that fixed actor, hold canonical locks and the request lease through commit, issue no arbitrary SQL or shared binding, and never mount a user-selected route/actor. On the DB side use the verified effective original connection principal, not `current_user` inside a definer or an assumed pool identity; if the pool/Hyperdrive resolves a different/shared role or the mapping can be altered by the caller, fail closed. If the required boundary is autonomous DB-side proof of the actual Clerk request (including against a stolen dedicated credential), the pinned stack cannot meet it: review a separately designed audience/actor/operation/nonce/expiry bound verifier before activation. Do not add an actor-argument boolean wrapper pending that work. This addendum narrows the conditional earlier wrapper to private implementation detail only.

**Activation blockers:** current deployed ownership/ACL and complete all-state job visibility under FORCE RLS, exact one-actor/one-scope provisioning authority and immutable mapping, approved private connection/EXECUTE and bounded purpose-command contract, shared canonical lock ordering and post-lock snapshot/read visibility, actual lease/abort and verified COMMIT acknowledgement behavior, and approved real-account validation before rollout. Reviewed SQL/ACL/config changes require separate approval, not implied by local review. Legacy identifiable audit/receipt pairs, destructive cleanup/replay, completed security tombstones and retention scope remain separate gates before **new or replayed** Teacher writes can be enabled; this predicate establishes deletion-clear at that instant, not erasure compatibility.
