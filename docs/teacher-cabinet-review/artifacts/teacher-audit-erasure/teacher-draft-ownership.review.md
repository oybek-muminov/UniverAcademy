Product rule: a Teacher must publish or explicitly cancel each draft before starting account deletion. Group handoff is optional. Do not automate either transition.

## Private state and staged validation

* Proposed private `test_versions.draft_owner_person_id`: nullable UUID referencing `people.id`, ON DELETE RESTRICT, no automatic nulling or cascading. Add a partial btree index keyed by owner for non-NULL rows; deletion preflight searches any owner row (including an invalid status), not just currently visible drafts. No owner IDs in public DTOs, wire, snapshot, or raw responses.
* Pair nullable ownership with trusted classification. Proposed closed `draft_origin` marker for active drafts only, with values Teacher/platform and a transitional unknown (NULL); it is set by the command, not an HTTP/body field. Valid tuples after validation: active Teacher draft + exact non-NULL owner; active explicitly platform draft + NULL owner; any non-draft + NULL owner and NULL origin. If platform-owned drafts do not exist in observed inventory, omit the platform class and require an owner on all drafts. Historical unknowns are not platform drafts. Any unresolved possible Teacher draft blocks account-deletion starts conservatively until classifiable with authoritative provenance, without guessing among people. Individual no-draft proof for legacy rows requires authoritative exclusion for that exact person; no such proof exists in the pinned catalog.
* Stage nullable columns with no ownership default. Freeze old/unknown draft writers until all entry points are identified and use the required protocol. Inventory privately, reconcile using only authoritative records (not current role, subject, group, a first receipt, or timestamps), and validate tuples before enabling affected deletion or writing routes. Keep authoritative legacy-coverage gate closed if inventory/snapshot or any writer coverage is incomplete. The legacy status is text in the catalog; inventory the accepted contract, readers, validators, and storage semantics before changing it. Require an explicit terminal `cancelled` path with coordinated read/write behavior, or a separately reviewed private terminal marker if public status cannot change yet; do not recycle `archived`, expose an unsupported enum value, or infer absence of drafts from a status label. Pinned storage recognizes group archive and has no cancel command. No cancel persistence is implemented here.

## Transaction and route boundaries

1. Create: in the proposed first-draft adapter (locked-rows-hardened.patch, version insert around line 115), after fresh verified mapping, actor/pilot authority and authoritative deletion-clear, set exact owner from locked person and Teacher classification in the same insert/commit. Never take owner from caller. Any published record has no draft owner. No independent ownership transfer, reopen, or owner-clearing patch.
2. Mutate: pinned storage/staff-first-test-rows.ts around lines 36–51, 68–99 and 150–156 identifies metadata/questions/publish, locks version and CASes old draft revision, but presently relies on subject/role and lacks owner/cancel. In all Teacher draft mutations, verify exact ownership before prior receipt lookup/disclosure or mutation; respect existing permissions as additional conditions. Any separately authorized cross-person operation affecting ownership would need the authoritative person hint rechecked under locks before version access, with all involved people locked in existing sorted order; no new Admin capability, override, or generic RPC. Same-lock freshness through commit applies to create/edit/publish/cancel/replay and all alternative writers; fail and retry conflicts in canonical order instead of locking a person after a version. For erasure, lock the actual Teacher even if current role/group has already been removed.
3. Publish: only existing valid publish semantics with exact owner and revision CAS. Save the valid immutable published snapshot and status, clear draft ownership/classification in the same commit; preserve version/demo IDs, assignments, publication/timing rules, and student state. Thereafter existing Owner/scoped Admin authority applies as before, without a substitute Teacher or permission expansion. Existing draft-only storage CAS does not establish new post-publication editing powers.
4. Cancel: new explicit confirmed Teacher action, not metadata PATCH or archive. Under owner/person and version locks/CAS, verify never published, no snapshot or references representing assignment/history; these reference checks must include concurrent assignment paths under existing lock protocol, not a filtered UI count. Atomically enter an irreversible nonassignable terminal state and clear owner/classification. Any separately reviewed disposition of unpublished content must not touch Student data. Publication/cancel compete on the same locked version/revision, only one can win. Delayed or stale requests must not revive the draft or turn an erased receipt into a new command.
5. Deletion: pinned supabase/proposals/account-deletion-rebuild.review.sql lines 65–95 show Clerk advisory → identity mapping → person row locks before the deletion-job insert. Add the no-drafts/inventory gate under this lock in the authoritative internal deletion transaction, before any first job, disabling, tombstone, or provider mutation; surface “publish or cancel drafts” without exposing unrelated users. A fresh post-lock complete read is required: an older transaction snapshot, RLS-hidden rows, or lack of read access are not negative evidence; keep gate closed unless current executor has narrowly verified authoritative visibility, with any later SQL/ACL review separate. Repeat assertion before final DB removal as defense in depth (restrictive FK prevents silent unlink; it does not undo provider actions). If draft commits first it blocks deletion; if deletion starts first the existing deletion-clear barrier blocks create, including retries/replays. Keep role/group and immutable audit/receipt erasure checks separate and intact.
