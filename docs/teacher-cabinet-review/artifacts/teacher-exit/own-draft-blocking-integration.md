# Teacher account exit: unresolved own drafts (offline contract)

Owner decision: do not start account deletion while any own draft remains. Teacher deliberately publishes or cancels each. Neither leaving the screen, role removal, a background job, nor account deletion itself takes either action. Published tests, assignments, Student attempts/results/history and deadlines survive independently; Owner/Admin may use only their already authorized management actions.

## Pinned baseline

- Teacher Web port is load/switch/sign-out only (apps/teacher-web/src/port.d.ts). The separate local manual editor only saves a question via a delegated authenticated port; it does not publish, cancel or start deletion.
- Existing publish is POST /api/v1/admin/versions/{version_id}/publish (staff-http.ts:76–100), exact expected_revision and explicit reason (Publish schema), existing Idempotency-Key receipts, verified current Clerk/staff/approved subject or existing permitted owner authority. staff-content.ts:49–79 validates draft, question integrity and ordinary grading and freezes the immutable snapshot. Publishing does not assign a group or change deadlines. A same-key replay returns existing authorized state; refresh rather than invent success on uncertain delivery. The exit screen must not bypass any of these checks or use its advisory list as authorization.
- There is no published contract path or canonical operation for draft cancellation: Version status is draft|published and staff-content.ts only edits/freezes; the other cancellation paths are Student attempt/recovery or assignment concepts. “Delete content”, “archive test”, or “cancel a Student attempt” are not equivalents.
- Current account-deletion HTTP accepts a candidate receipt and returns pending; the Mini App controller's submit contract is pending or a recognized rejection, otherwise it retains the receipt and checks status. No authoritative blocking-drafts response or Teacher transport exists today.

## Required own-only contract

1. Under independent fresh Clerk proof, resolve the same canonical actor/person; return only this Teacher's currently unresolved draft version IDs, current revisions, and labels needed for the UI. Scope, subject approval, draft editor rights and ownership are different facts; never use a subject-wide catalog or title to infer ownership. The pinned version/demo rows have no durable author/owner field for all drafts; a new create receipt/audit can prove only its own generation until audit erasure design supplies a durable ownership proof. Incomplete or ambiguous ownership fails unavailable, not “no drafts.” Do not disclose other teachers' IDs, questions, people or scores. No-store and discard stale identity/generation results.
2. This screen is advisory. Inside the existing account-deletion preflight person lock, check authoritative complete own unresolved draft state **before** writing a job, disabling person/provider/session or starting any cleanup. Return a definitive dedicated draft-blocked branch only when no deletion job was created and owner set is verified; other failures retain existing commit-unknown/status behavior. The draft creation/cancellation, publish and deletion paths must share the same canonical actor/person plus draft/resource lock ordering or an equivalent serialization guarantee, so creating another draft cannot race a false-clear deletion. Existing staff erasure gates remain independent.
3. List exact rows and offer explicit “Nashr qilish” (normal authoring/publish flow with revision and reason) or “Qoralamani bekor qilish” only after a real draft-only contract ships. Do not generate a reason, publish an invalid/empty draft, or offer deceptively working Cancel. On confirmed publish or cancellation refresh the authoritative list. Discard a local pre-dispatch deletion receipt/intent only on a definitive server guarantee that no job exists; otherwise inspect status and never create a competing request. Even if the list empties, do not resubmit, queue, or continue deletion. Only a new explicit user request with fresh confirmation and reauthentication can attempt deletion again.
4. Missing cancellation contract: make it a named irreversible draft-only terminal domain transition (proposed status/tombstone, no API/schema added), authorized on current same-person owning Teacher, exact draft version plus revision compare-and-set, explicit confirmation and stable idempotency, under the same locks. Reject published/snapshot or any assignment/attempt dependencies; do not alter another draft, group links, published content or Student rows. Resolve conflicts by canonical read; no automatic cancellation. Audit atomic with transition and compatible with approved eventual staff erasure. Update Version validation/storage and deletion-block query together so only still-unresolved drafts block; retain history per approved policy rather than treating cancellation as physical content deletion.
5. Preserve immutable published test/domain IDs and refs independent of the departed Teacher's identity. Ownership/audit erasure design must retain content and authorized Owner/Admin management, without granting new powers, and verify history/answer keys/timers remain unchanged. Review artifact only; no source/fixtures/build/DB/runtime/deployment changes.
