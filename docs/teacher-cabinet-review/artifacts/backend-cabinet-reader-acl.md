# Cabinet helper security and ACL review gate

Review only. No executable SQL, no application bind/route/deployment, no production access from this task. Uses pinned source `3dbb714f2f758c7dbe03548a71c161718cf9cb53` and the lead's separate live catalog-only findings: forced RLS, no direct `ua_runtime` SELECT/policy for required staff tables, person-scoped domain-phase policies for attempts/series, no verified g2 role.

## What authorizes the read

- `ua.phase`, `ua.person_id`, `ua.person_ids`, `ua.clerk_issuer`, and `ua.clerk_subject` are caller-mutable PostgreSQL custom settings. They can restrict query phase and catch mismatches within the trusted Worker, but cannot authenticate a function caller, protect against a forged ordinary SQL request, or authorize a privileged cross-table staff lookup by themselves. Do not use a person UUID, provider subject, or an already stored digest as the helper credential.
- Existing Worker must first verify the **raw current opaque access bearer** through its Clerk-bound student transaction and fresh Clerk provider-liveness lease, and recheck before commit. Pinned `student-state.ts:94–110` shows 32 random bytes hex-encoded into 64 lowercase characters and SHA-256 over the UTF-8 token. A narrowly privileged helper, if ultimately reviewed, accepts the raw token only as a bound DB parameter; validates exact format; computes the digest inside the helper; resolves by indexed digest with no arbitrary person selection; and requires the current not-superseded, unexpired access proof and enabled, unrevoked, unexpired Clerk family. Request-supplied expected person/family/Clerk tuple can at most be an additional equality assertion after independently deriving the binding.
- Under DB clock and the existing canonical person lock, recheck the exact immutable `clerk_family_bindings` family/issuer/subject/sid/person tuple, active `clerk_student_sessions` matching all fields and with `retired_at_ms IS NULL`, and enabled matching `clerk_identities`/person. Verify the same locked person remains an enabled student with mirrored SQL/JSON roles. The helper may check phase/context consistency only after proof derivation. Worker holds the existing expiry lease and must reject on superseded session, cancellation, unexpected tuples or any failed/revoked liveness; never rely on DB binding as proof of upstream Clerk's current status. Do not infer that raw-token binding establishes provider liveness for a direct SQL invocation.
- Return only a same-person staff capability result, not raw grants, phase, provider metadata, secrets, subject identifiers, or admin scope. Authoritative bit requires enabled teacher role, approved staff access and at least one currently approved/unrevoked subject. Missing/no-match/revoked is generic no capability. The Worker uses the existing authorized person-scoped domain-phase reader separately for current exam-series/attempt projection; do not give the helper access to questions, answers, result history, or staff management.
- A digest-only helper would let a caller replay stored values if SQL access can read ledger rows; raw-token hashing prevents simple digest reuse under the cryptographic preimage assumption, not theft of a raw bearer. The helper result is navigation only and may never grant Teacher/API scope. If the requirement is that even someone with an app DB credential and a stolen raw bearer cannot query this bit while upstream provider liveness fails, a helper executable by that role does not meet it. Use a narrower preauthorized app-owned reader issued only to the trusted verifier under a separately reviewed service identity, or a proof independently verifiable by the reader and unavailable to that caller; do not add custom crypto or a role now.

## Exact ACL acceptance checks before drafting executable migration

- Verify deployed table names, types/domains, functions, locks/freeze, digest/expiry semantics and real role membership. Choose a separately reviewed, dedicated function-owner role that cannot log in, inherit, bypass RLS, create roles, databases, schemas or extensions, or be acquired with SET ROLE by Worker/application/untrusted roles. No existing broad owner shall define this helper. Grant owner only explicit column reads and controlled SELECT policies required for the proof and capability, never UPDATE or membership in data-owning roles. Forced RLS remains; the helper's owner role has its own reviewed policies, not extra table grants to `ua_runtime`. Review privilege of every existing policy/function helper referenced.
- Fully qualify all objects, operators/helpers where warranted, and lock down search path; do not let a writable schema or temp function shadow dependencies. No dynamic SQL or user-supplied identifiers. Define ACL in a single transaction with default PUBLIC EXECUTE removed, deny unrelated application roles and PUBLIC, approve only the exact intended EXECUTE (if using independently bound raw proof and reviewed trust boundary). Require no new general SELECT on staff tables, no extra exposed function/HTTP path, no unsafe inheritance and no session-setting trust escalation. Catalog before/after and narrowly switched role review are separate approved steps.
- Do not expose or persist raw bearer values in query texts, logs, errors, pg_stat views, diagnostics or audit. Use parameterization, query caching off, verified origin TLS, and independently verify Postgres logging/error parameters, Hyperdrive telemetry and caller code handling across the denied/success paths. Return bounded generic faults. Unconfirmed logging/transport, owner ACL, installed function history, current authorization lease or policy allowlists are blockers, not details to guess.
- Activation is separately approved. Real designated-account verification only; do not apply migration, run SQL, use fixtures, or grant/revoke Teacher as part of this stage. Approved appointment operation remains deferred.
