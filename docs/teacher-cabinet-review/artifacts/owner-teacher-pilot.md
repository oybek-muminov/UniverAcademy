- `tests/account-deletion/schema-catalog.json`: copied catalog, not live validation. The snapshot does not show a subject FK for approvals or a standalone canonical subject table. Never infer approval IDs from arbitrary labels or mint IDs to satisfy the operation.
- `tests/account-deletion/schema-review-scope.md`: copied columns/PK/unique/FKs are sourced from a read-only production catalog, but the fixture omits production CHECKs, defaults, RLS, triggers, ownership and function definitions. Do not substitute the fixture or GitHub source for current catalog confirmation.
- `storage/staff-first-test-rows.ts:184–188` and copied catalog: staff receipt/audit has an atomic pair with mutually deferred FKs; audit needs command key, attributed actor, action, target, revision and DB time. Existing convention is not an accepted grant/revoke contract. Inspect the actually installed deletion behavior; do not promise ordinary self-service deletion after a pilot promotion/demotion and do not remove audit/security records as a shortcut.
- `staff-state.ts:77–89` and `staff-http.ts`: existing subject approval is not general group/Admin authority; several provisional roster mutations are owner/admin-only. This appointment is not sufficient to make the planned Teacher cabinet or group controls operational.

## Transaction design once reviewed

- Invocation is one bounded explicit transaction. Match current lock protocol, not an ad hoc table lock: known auth/deletion takes verified Clerk identity advisory lock, current mapping, then person; staff writers lock affected people in sorted order. Backend must review owner+target lock ordering and concurrent appointment, auth, staff command and account deletion writers against production. Re-check actor permission and target identity, enabled state, deletion state, canonical approvals and expected versions under lock; break on unexpected schema or row counts. No manual write bypassing freeze guards.
- Initial pilot target is a confirmed existing student (one student identity); reject targets with Owner/Admin, unrecognized/duplicate role data or pre-existing broad management rights. Reject differing DB/JSON roles and do not silently repair historical inconsistencies. Assert expected before/after with exact counts; only append or remove the single teacher role in both SQL array and JSON array, preserving order of all other roles. Verify other profile content and person ID do not change.
- Grant requires at least one selected real subject. Create or enable only the narrow needed `staff_access` row, with `approved=true` and `manage_roster=false`, `manage_content=false`, `all_groups=false`, `all_subjects=false` for a clean pilot target. Never overwrite an unexpected existing staff record. Add only selected subject rows, or explicitly reapprove a previously revoked selected row under authority and expected pre-state; never reactivate unrelated rows. `teacher_subject_approvals` is separate from `staff_subject_scope`; don't copy approvals into general scope.
- Revoke selected active subjects by marking only matching teacher approval rows revoked using the DB clock; preserve historical records and unselected approvals. If the explicit command is complete teacher demotion, verify and end all remaining teacher approvals, remove only teacher from both role representations and arrange reviewed disabling of the teacher-only staff gate; preserve student role, identity, history and active attempt. Never remove Admin/Owner, remove sessions, force sign-out, delete scope or audit history, or do a provider role write. Partial revoke does not remove teacher while an approved subject remains.
- Commit only after post-state guards and the reviewed audit path succeed. A repeat with the same approved operation ID and exact target/mode/subjects must be a verified no-op or return the saved reviewed outcome, never duplicate audit or undo a later revoke. On mismatched payload, pre-state, or later changes, stop rather than silently apply. After a timeout/lost ACK, re-read exact state & command record; do not blindly rerun. Revoke is a separate approved operation, not a generic rollback after a successful grant.

After approval and deployment, verify with a designated real account: same identity signs in, teacher visibility restricted to intended subjects, no broader grants, active student test/history stays intact, and revoked subjects/teacher direct URL/API no longer authorize. No synthetic data. Design dependencies remain: current live catalog, canonical subject authority, approved actor/audit lifecycle, teacher routing endpoint and live scoped teacher adapter.
